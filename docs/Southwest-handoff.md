## 验收方法

1. 固定 engine、persona、客户端与参考 Chrome 版本/OS，记录查询产品、航线、日期、人数、币种、时段及网络出口。参考 Chrome 必须在可比条件下成功；对照失败时结果标为无法判定，不归罪于某个内核。
2. Obscura 独立建立自己的正常会话，经真实页面/RPA 主链查询；不借用 Chrome Cookie/token，不以接口重放、缓存或模拟响应代替验收。
3. shopping 不再返回 403 或相应业务拒绝码；响应不是挑战页/软错误，航班/报价结构和查询条件相符，结果可被使用方消费。无库存样本单独记录，不代替有可售结果的成功样本。
4. 执行前确定查询集、轮数、间隔和持续观察窗口，覆盖新会话与复用会话；保留每轮失败和重试，不以一次 200 关闭。只验收到查询/报价，不执行购票付款。
5. 保存脱敏的对照条件、请求链与响应校验、时序、错误码和结果摘要。凭据、Cookie/token、原始会话材料不入库。403 重现时任务保持未关闭。

## 差异定位

按完整证据链比较：统一 persona → 实际 primp 出口/TLS/H2/头与请求体 → Cookie/存储和页面生命周期 → frame/Worker/脚本与事件 → shopping 业务结果。采集扰动须有对照，不能仅凭 Cookie 名称、令牌长度、错误措辞或 JA3/JA4 推断原因。

发现的 Chrome 行为差异缩减为通用 fixture，经 OB-045 分配到既有 Cookie/网络、realm/观察、Worker/frame、Beacon、IndexedDB 任务。保留现有回归，不做 hostname 专属布局、网络或身份补丁。

此业务验收与通用协议/Web API、隐私隔离、性能及发布门禁并行成立。通过是该受测流程的重要成功证据，不单独证明所有网站无法关联身份或价格歧视已经消除。旧调查过程和已合入补丁可从 `e67e67b` 及此前 Git 历史追溯，不再维护流水账。
